§2 SYSTEM & OPERATIONS

WORKFLOW: display name "Sync Training Data" (fetch_activities.yml). Fires FOUR times each morning — '0 4 * * *', '0 5 * * *', '0 6 * * *', '0 7 * * *' UTC (covers ~06:00-09:00 Danish time across both DST states) — rather than the older single-hour-check design. GitHub's scheduled cron is best-effort and frequently delayed/dropped, so firing four times makes it very likely at least one lands each morning. A run-gate step (dst_check) makes every fire after the day's first successful fetch a no-op: it reads fetch_status.json's last_success_date, compares against today's Danish-local date via `TZ='Europe/Copenhagen' date +%F`, and only proceeds if they differ. Net effect: whichever cron fires first (even delayed) does the day's real update; every later fire that day is a genuine no-op (Python never even runs); if a fetch genuinely fails, last_success_date stays stale and the NEXT cron that morning automatically retries with no human action needed. workflow_dispatch always bypasses the gate and additionally exposes a `full_refresh` boolean input.

Two Python steps, both gated by the same dst_check condition: "Run fetch script" (fetch_activities.py; env: GARMIN_EMAIL/PASSWORD, POLAR_ACCESS_TOKEN, POLAR_USER_ID, FULL_REFRESH) and "Build dashboard metrics + AI coach" (build_dashboard.py; env: ANTHROPIC_API_KEY only — fetch no longer calls Claude).

FULL_REFRESH: rebuilds runs.csv/strength.csv from Garmin's complete history instead of incrementally. Triggers: first Sunday of the month (automatic, regardless of checkbox — CONFIRMED observed live), FULL_REFRESH=true env var, or the manual workflow_dispatch checkbox. Determined at runtime, not by which cron fired. Governs fetch_activities.py only; build_dashboard.py always aggregates whatever's on disk regardless of mode.

GIT-ADD LIST (third workflow step — CURRENT, 18 entries; hikes.csv, garmin_fitness_metrics.csv, polar_cardio_load.csv, polar_exercises.csv, polar_pending_transaction.json, and model_ab_log.json are all CONFIRMED present, closing out several previously-flagged pending items):

PUSH RETRY (fetch_activities.yml): the commit/push step retries on rejection (up to 5 attempts) via `git fetch origin main` + `git reset --soft origin/main` + re-commit — safe because every file this workflow commits is fully regenerated from source each run (none hand-edited). This replaced an earlier `git rebase`-based retry that caused a real duplication bug: two commits that each contain a full independent rewrite of the same CSV look to git like two non-conflicting sets of added lines, so rebase's line-based 3-way merge silently interleaved BOTH versions, duplicating every row exactly once. `git reset --soft` avoids this by moving the branch pointer without touching the working tree, so freshly-written files simply become uncommitted changes on top of the new remote HEAD and get re-committed as one clean snapshot. Do not reintroduce a rebase-based retry without re-confirming this reasoning.

CHECK DASHBOARD COVERAGE WORKFLOW: display name "Check Dashboard Coverage" (check_dashboard_coverage.yml), separate from Sync Training Data — no Garmin/Polar login, runs fast. Triggers on push/PR touching build_dashboard.py, index.html, or check_dashboard_coverage.py itself, plus workflow_dispatch. Single step: python3 check_dashboard_coverage.py, exit 0 = pass. NOT currently enforced via branch protection — it shows red/green in the Actions tab and PR checks but doesn't itself block a merge. To make it a hard block: Settings → Branches → branch protection rule on main → require this check to pass. Two-layer design (Layer 1 auto-derived key coverage from build_dashboard.py's dict literals; Layer 2 hand-maintained MARKERS + REGRESSION GUARDS) — CONFIRMED both layers are current as of this writing (see DASHBOARD COVERAGE CHECK in §1); the script passes clean with 0 failures against the live repo.

THIRD WORKFLOW — Receive Steps Data (receive_steps.yml): triggered by repository_dispatch (type "health-steps") from the Pipedream → iPhone Health Auto Export automation, or manually via workflow_dispatch. Parses a JSON payload of {date, steps} entries, merges into steps.csv keyed by date, commits directly — no retry/reset logic, since this fires independently of the daily sync and collisions on a single-file commit are rare/low-stakes.

5c. HR SOURCE PHILOSOPHY — unified, covers runs AND strength (build_run_hr_context() / build_strength_hr_context() in build_dashboard.py)
Per explicit athlete direction, the Polar-overlap/fallback logic applies anywhere Garmin/H10 has no pulse — not just occasional run dropouts, but EVERY strength session (which never has H10 data at all, ever, since no strap is worn while lifting). These two unified functions replaced the previously-separate build_strength_hr_overlay() and build_hr_dropout_fallback():
- build_run_hr_context(): one entry per run with any HR data (Garmin OR Polar-fallback), keyed by activity_id. source == "garmin" uses real per-second run_hr_samples.csv data for a genuine time-weighted zone-minute breakdown. source == "exercise"/"continuous" (H10 dropout) uses a calibrated Polar estimate (offset derived from real Garmin-vs-Polar comparison data, self-correcting as more accumulates) plus, for the continuous-HR case only, a zone breakdown computed by weighting individual raw samples equally rather than time-weighting (Polar's continuous HR is event-driven, not a clean time grid).
- build_strength_hr_context(): every strength session, always Polar-derived (calibrated against the same continuous-HR offset — a deliberate judgment call, since the offset itself was derived from RUNNING comparisons and there's no way to get a strength-specific calibration; worth revisiting if that ever becomes possible), with the same zone-breakdown treatment as the run-side continuous-HR case.
Both surface max_hr AND a per-session zone-minute breakdown (e.g. "Z1 12m Z2 8m Z5 4m"), not just a single averaged HR number — this fixes a real accuracy gap the athlete found: a run with several hard sprints and easy recovery between them averaged out to look identical to a genuinely steady easy run when the coach's prompt only ever saw one averaged number. MODEL: claude-opus-4-8, "thinking": {"type": "disabled"}. max_tokens=1600 (raised from 700 — the 700 cap CONFIRMED to truncate live on the first real post-redesign run, cutting output after the TRENDS section and leaving 5 of 7 sections plus WATCH as empty strings; the parser correctly populated what arrived and left the rest empty, so nothing crashed, but 5 sections silently never generated). PRICE_INPUT_PER_M/PRICE_OUTPUT_PER_M = 5.00/25.00, USD_TO_DKK = 6.90.

OUTPUT STRUCTURE: the old 4-section HEADLINE/SUMMARY/EVIDENCE/WATCH format is GONE. Current 9-section format, regex-parsed with defensive fallback:
- HEADLINE: up to 3 short sentences (~30 words total, stop well under 45). Single most important takeaway across ALL of training, not one metric. Not a generic state label. No numbers cited.
- OVERVIEW: one paragraph covering Running, Strength, Steps, Intensity Minutes, Recovery, and Load TOGETHER as one coherent picture — deliberately the athlete's own explicit design, both for coherence and for cost.
- TRENDS: one paragraph covering the 16-week weekly trend and the annual monthly progression together.
- THRESHOLD: one paragraph on LT + VO2max together.
- ZONES: one paragraph on time-in-zone distribution, informed by a PER-SESSION HR SHAPE block (not just the weekly aggregate).
- HR_COMPARISON: one paragraph on strength-session HR + the Garmin-vs-Polar comparison data together. Fine as a single plain sentence if nothing's notable.
- CALENDAR: one paragraph on consistency/frequency patterns, distinct from the deterministic streak-count line already shown.
- PERSONAL_BESTS: one paragraph on whether any PBs are within realistic reach or how they relate to current focus. Fine as a single plain sentence if nothing's relevant.
- WATCH: 2-4 bullets, NOT trimmed despite an early instinct to shrink it for token savings — WATCH items are not merely reader-facing, they ARE the coach's own continuity mechanism (persisted into coach_context.json, read back verbatim as "Things flagged to watch as of [date]" in the next day's RECENT COACHING HISTORY block). Shrinking WATCH would degrade the coach's own memory quality, not just trim something cosmetic.

CRITICAL DESIGN PRINCIPLE: every section is explicitly instructed NOT to restate specific numeric figures (distances, paces, HR values, percentages, session counts) — every number is already shown directly on the dashboard card that section renders next to. Sections are interpretation-only. This preserves the old EVIDENCE mechanism's zero-fabrication guarantee (the model never had to reproduce a number, since Python always wrote every number that appeared) WITHOUT needing the evidence-selection machinery itself.

EVIDENCE CATALOG and DIGEST: RETIRED ENTIRELY (see §6). Do not re-add without a real reason — this was a deliberate, athlete-directed simplification, not an oversight.

PARSE_COACH_SECTIONS(): SECTION_KEYS/SECTION_DELIMITERS constants define the 7 group names and their regex delimiters. Graceful fallback: if HEADLINE can't be found at all, the entire raw text is dumped into the "overview" section so something still renders; a genuinely failed/fallback day still writes NO coach_context.json entry.

COACH_SUMMARY.JSON SHAPE: last_updated, headline, confidence_pct/label/reasons/attention, sections (dict: overview/trends/threshold/zones/hr_comparison/calendar/personal_bests, each a string), watch_items, usage + MTD/YTD cost fields. No evidence_items, insights, summary, or quiet field — all gone, not renamed.

COACH_CONTEXT.JSON (memory): {history: [{date, headline, watch_items}, ...]}, capped at 5, still the sole continuity mechanism, still deliberately not block-phase-aware.

MODEL A/B SHADOW-LOG EXPERIMENT (14-day trial, model_ab_log.json, CONFIRMED LIVE and running, not just designed): pure side-logging with ZERO effect on what the dashboard renders — the live coach stays Opus 4.8 and coach_summary.json is written exactly as before. Fires only when the live Opus call genuinely succeeded (never shadows a fallback/failed day), entirely wrapped in try/except so any failure here can never affect the live coach output or fail the build. Sequence: (1) a parallel call to claude-sonnet-5 on the IDENTICAL system_prompt + user_prompt; (2) blind A/B assignment (which output is "A" vs "B" randomized per run so a judge can't pattern-match on position); (3) a judge call (also claude-opus-4-8) scores both outputs blind against a 4-criterion rubric (context_awareness, artefact_handling, no_fabrication, coaching_usefulness — each 1-5 with a one-line reason), strict JSON, states an overall preference — parsed defensively (falls back to extracting the first {...} block, then to a {"parse_error": true, "raw_text": ...} shape rather than crashing); (4) one full record appended to model_ab_log.json (date, ab_mapping, both raw outputs, both cost breakdowns, judge result + its own cost). SONNET_PRICE_INPUT_PER_M/OUTPUT_PER_M = 3.00/15.00, SHADOW_MAX_TOKENS = 1600. The judge is ADVISORY ONLY — never auto-selects or eliminates a model; the athlete reads the paired outputs personally and makes the call, since the athlete is the actual consumer and the only real ground truth for subjective coaching quality. Judge is Opus (NOT Fable) deliberately: bounded rubric-scoring, not long-horizon reasoning, so Fable's tier-above capability is unused, and Fable also carries mandatory 30-day retention/no-ZDR, the wrong tradeoff for routing health data just to grade paragraphs. Cost during the trial: roughly +$0.02-0.03/day for the Sonnet shadow + judge calls on top of normal Opus cost — cost and value are in different units with no objective exchange rate, so at one-call-a-day the decision is ~95% "which reads better to the athlete," not a cost optimization. After the trial concludes: athlete decides whether to keep it running, stop it, or let the accumulated judge data inform a future model choice — the harness itself should then be removed or gated off, not left running indefinitely by default.
